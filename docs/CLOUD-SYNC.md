# Optional cloud synchronization

Status: journal integrated with local mutations and native capture inbox, atomic persistence in existing notes.json, conflict projection and explicit resolution UI, Cloud Sync settings show local-only status. No live provider connected and no user data uploaded. Legacy libraries are initialized locally; downgrading to builds that do not preserve the journal is unsupported.

## Provider selection

Default local-only. One active account/provider at a time. Switching provider requires an explicit merge/import review, never blindly copies an entire library or treats missing records as deletes. Keep local note data available offline. Bind sync state to provider + account + library namespace; no automatic cross-account upload.

- iCloud: CloudKit private database, shared explicit container for both bundle identifiers, CKAsset for large HTML/image payloads. Requires Apple Developer team, signing/provisioning with iCloud entitlement, actual container/schema, same Apple account on review devices. No production entitlement added to existing unsigned development build.
- Google Drive: Drive API v3 appDataFolder (drive.appdata scope), native OAuth on macOS/iOS with appropriate platform client IDs under the same Google Cloud project, native secure auth flow and Keychain token storage. No broad Drive permissions, embedded client secrets, or service account. Cross-platform account/appDataFolder interoperability must be validated with real credentials.

## Data and conflict safety

Do not synchronize notes.json directly. Immutable per-key revisions contain note payload or tag color and parents, and explicit deletion tombstones. Journal merge is atomic, idempotent and independent of clock order. Concurrent divergent edits/delete-versus-edit remain unresolved, retaining both versions until explicitly resolved. Large payload transport, chunking/checksums, per-provider incremental listing/pagination, retry and account handling remain to implement. Revision history grows until a safe retention/compaction policy is proven. This foundation intentionally does not alter existing note data.

## CloudKit transport prototype
The native adapter uses a private custom zone, immutable record names (revision UUID), CKAsset JSON payload and SHA-256 verification. It verifies the expected account/namespace before each exchange and upload, pages full queries, orders uploads parent-first and rejects nonidentical record collisions. The protocol is exercised against an in-memory provider. The adapter is **not instantiated in the review build**; no real CloudKit operation runs without signed container setup, persisted account binding, explicit consent and app-level coordinator. Configure NoteRevisionV1 schema/query indexes and test with an actual signed app before enabling. The current full-history design retains deleted content and can grow substantially; implement retention/storage policy and user-facing permanent deletion before release. No automatic migration of cloud identities or data. No live provider validation yet.

## Enrollment and transaction stage (R5)
Persist SyncEnrollment with notes.json. A first enrollment requires explicit consent to replace the pre-cloud revision history with a snapshot of current live clips/tag colors; this deliberately does not upload previously deleted content. Current clips remain unchanged, unresolved pre-cloud conflicts block enrollment. Pausing retains the binding and history; another account or provider cannot silently take over. No migration/forget action is exposed yet. SyncCycle uses a single main-actor library owner, validates a complete remote graph, reads the newest local snapshot after network awaits, persists merged data before upload, checks account/pause/cancellation, and bounds history transfer (review ceiling 4000 revisions, 128 MiB per revision, 256 MiB total). Limits block sync without removing data; not a permanent deletion/compaction implementation. CloudKit fetch also checks counts and byte sizes before decoding assets. No network calls or enrollment in the unsigned review build. Signed shared container, explicit consent UI, foreground scheduling, retry/status handling and actual CloudKit acceptance remain next. Before a general release implement retention/permanent deletion with safe multi-device semantics. The first baseline replacement must be plainly explained in the consent UI; do not call it silently.

## Signed development review UI
CloudSyncController, CloudKitSettingsSection and SyncForegroundSchedule are connected to the app. Default builds have no CLIP_CLOUDKIT_REVIEW compilation condition and never instantiate CKContainer. Only explicit signed Development review builds may expose connection. Account check is read-only; the user must confirm the baseline replacement and cloud upload warning. Sync now, pause/resume and foreground checks (at most once per minute, no guaranteed background delivery) reuse the same coordinator. A paused binding never authorizes another account; account mismatch blocks exchange. Pause is only available between sync cycles; already-submitted requests are not revocable. Last success is session-local. No production activation until retention/permanent deletion and real account tests.

For the separately authorized signing lane: register com.ioant.clip.macos and com.ioant.clip.ios under the same Apple Developer team; attach the same actual iCloud container to both; configure development provisioning for CloudKit. Use Config/CloudKitReview.entitlements and Config/CloudKitReview-Info.plist as product-owned templates. Explicit build overrides: `CLIP_CLOUDKIT_CONTAINER` (actual registered ID), `CODE_SIGN_ENTITLEMENTS=Config/CloudKitReview.entitlements`, `INFOPLIST_FILE=Config/CloudKitReview-Info.plist`, `SWIFT_ACTIVE_COMPILATION_CONDITIONS=$(inherited) CLIP_CLOUDKIT_REVIEW`, and real signing team/profile. Inspect the signed bundle entitlements and Info.plist for the same container and Development environment on both devices before installation; do not assume signing based on build success. Configure NoteRevisionV1 and its query index in CloudKit Console and validate with a separate test library/account before user data. No actual team/container identifier is guessed or committed. See Apple: https://developer.apple.com/documentation/xcode/configuring-icloud-services/ and https://developer.apple.com/documentation/cloudkit/enabling-cloudkit-in-your-app .

Review builds compile with a separate Application Support directory `ioant-Clip-CloudKit-Review`, even if container configuration is absent, so they never load or migrate the existing `ioant-Note` daily library. The existing browser host still targets the daily inbox; for signed review use synthetic clipboard samples or manually imported test captures, not the daily browser bridge. Do not replace the normal installed app with a signed review build without separate approval. Both compilation modes and absence-of-configuration behavior are tested locally without contacting CloudKit.

## Local signing prerequisite inventory
Run `bash scripts/cloudkit/preflight.sh` to check locally installed, nonexpired, explicit development profiles for both existing bundle IDs and an intersection of team and CloudKit container. It reports counts only; no raw provisioning data, device identifiers or certificates. No network or portal changes. A matching pair is only a prerequisite, not proof of private key access, provisioning/device compatibility, signed build success, or actual cloud authorization. For a blocked inventory, configure the existing App IDs and shared container via Apple Developer and refresh the local profiles. Test the matcher with `PYTHONDONTWRITEBYTECODE=1 python3 scripts/cloudkit/test_profile_inventory.py`.

## Final product signing identifiers
Use `com.ioant.clip.macos`, `com.ioant.clip.ios` and the proposed shared `iCloud.com.ioant.clip` (must actually register/associate it). Old com.ioant.note.* identifiers are no longer signing targets. Do not reuse old provisioning profiles or change unrelated apps. The runtime container is still explicitly provided by the signed review build; no guessed container or cloud access in the default build.

## Scoped signed build lane
After the operator registers both Clip App IDs and associates the shared container, run `bash scripts/cloudkit/build_signed_review_mac.sh` or `bash scripts/cloudkit/build_signed_review_ios.sh`. These build only the existing registered Clip target using the verified Apple Development identity, team 64RS366WKG and confirmed iCloud.com.ioant.clip. Xcode automatic provisioning may create/update the target's own profile; no device registration flag, revocation command, install, launch or CloudKit calls. The build uses separate CloudKitReview DerivedData and the explicit review compilation condition. `verify_signed_review.py` checks actual bundle metadata, strict signature, team, CloudKit signed entitlements, embedded profile and public signing certificate membership before claiming success. Not a release build or a real cloud sync test.

## Isolated signed macOS transport smoke
The separate `CloudKitSmoke/macOS` build lane compiles a dedicated command-line entry point instead of ClipApp, with the same registered Development entitlement and an explicit signed plist marker. It does not initialize LibraryStore, open a window, install an app or read daily/review data. Build using `bash scripts/cloudkit/build_signed_smoke_mac.sh`; separately authorize actual network testing before `bash scripts/cloudkit/run_signed_smoke_mac.sh`. The run creates a fresh `ioantClipSmoke-<UUID>` private zone, checks the real signed account, writes only a synthetic note, retries the immutable revision, reads through a second transport, edits and writes a deletion tombstone, and verifies the exact graph. Read retries are bounded. No user content, production, or normal revision zone is touched. Synthetic zones are retained for inspection; no automatic deletion or repeat after an uncertain write. This tests two transport instances on one Mac, not physical device sync. Schema/index or account errors are evidence, not a pass.
